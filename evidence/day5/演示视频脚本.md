# 智维 ZHIWEI · 演示视频脚本（3–5 分钟）

**录制前准备**
1. 打开展示页：`app/zhiwei-demo.html`（双击，浏览器全屏）
2. 打开 AGH Web 工作台：http://127.0.0.1:4180/ （备用镜头：Agent 执行时间线）
3. 终端窗口准备在 `zhiwei` 目录，用于展示"实时跑一遍"
4. 关闭通知；浏览器缩放 110%；分辨率 1920×1080

---

## 0:00–0:25　开场（问题）

**画面**：展示页标题页 + 设备示意（离心泵机组 P-101）
**旁白**：
> 工业现场的设备运维，长期依赖老师傅的经验：发现异常靠巡检，判断故障靠经验，修完还要再观察。
> 智维要做的，是让 AI 不只"说出哪里坏了"，而是**真的调用工具去修，并用数据证明自己修对了**。

## 0:25–1:00　方案架构

**画面**：切到展示页底部流程条 + AGH 工具列表（`agh mcp tools zhiwei-ops` 输出 9 个工具）
**旁白**：
> 智维运行在赛事指定的 Agnes Harness 上，模型只用 Agnes 3.0 Flash。
> 六个环节——数据读取、异常检测、故障诊断、维修方案、模拟维修、维修后验证——
> 全部由 Agent 通过 MCP 工具真实调用完成，每一步都留下可追溯的执行记录。

## 1:00–2:00　案例①正常 + 案例②边界

**画面**：展示页案例 A、B 卡片（放大健康度与时间线）
**旁白**：
> 案例一是正常设备：系统识别为健康，直接短路，**不误报、不维修**。
> 案例二是边界场景：故障幅度只有满强度的四分之一，检测结果是 warning、最大偏移 5.06σ——
> **刚刚越过阈值**。智维依然诊断出轴承磨损、置信度 0.981，一次维修后健康度从 60 回到 100。
> 说明它既能早期发现，也不会过度维修。

## 2:00–3:20　案例③失败与恢复（重点）

**画面**：展示页案例 C；随后切到 AGH 会话，展开工具调用链
**旁白**：
> 案例三是我们特意设计的"翻车现场"：故意把过载故障**误判成轴承磨损**，按错误方向去修。
> 第一次维修后验证直接不通过：残留 28.52σ，健康度只从 20 升到 50，
> 而且残留故障指向**过载**——电流和转速这两个过载独有的测点根本没回来。
> Agent 据此判断"维修目标错了"，重新规划，改按正确的主判故障维修，
> 第二次验证通过，健康度回到 100，最大残留 1.28σ。
> **关键在于：验证不通过时，它不会假装修好了。**

## 3:20–4:10　工程亮点

**画面**：终端实时跑一次 `python tools/validate_day4.py`；再展示 evidence 目录
**旁白**：
> 三个工程细节。第一，维修后数据一律以**维修前基线**为参照，否则"从第一秒就存在的残留故障"
> 会被当成正常而漏判。第二，所有过程都有 trace 与 JSON 记录，可回放、可复核。
> 第三，写盘类工具受 Agnes Harness 的审批闸门约束——**该拦的会拦，该留痕的会留痕**。
