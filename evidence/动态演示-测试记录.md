# 动态演示（交互式在线诊断）· 测试记录

日期：2026-10-14

## 一、什么是“动态演示”

除静态展示页（`app/zhiwei-demo.html`）与演示视频外，本项目还提供**可交互的动态演示**：
在网页上选择设备或上传一份电机运行数据，点击「开始智能诊断」，页面会实时显示
Agent 的规划步骤与每一次工具调用，最后给出故障诊断、维修方案与维修验证结果。

- **阶段一（工具链实时计算）**：与该作品同一套工具链（`tools/`）实时计算
  读数 → 趋势 → 异常检测 → 故障诊断 → 维修方案 → 模拟维修 → 维修验证。
- **阶段二（真实 Agent）**：真实启动 **Agnes Harness（AGH）** Agent，
  经 **MCP** 调用本项目 9 个工具完成同一条闭环，页面通过 SSE 实时展示调用过程。

## 二、如何运行（Windows + Python 3.11+）

```
# 1) 确认 AGH 守护进程已运行（见 AGH 官方安装指南）
# 2) 在项目根目录启动演示服务
cd app
.\start_demo.ps1
# 3) 浏览器打开
http://127.0.0.1:8801/
```

页面支持：设备下拉（M-001~M-005 / T-01~T-03）、上传 CSV、选择「维修前基线」、粘贴数据。

> 前置条件：本机已按赛事要求安装 Agnes Harness，并配置官方发放的 Agnes 模型 Key。
> 作品 ZIP 内已包含全部代码、数据与说明，可完全离线复现（展示页双击即可打开）。

## 三、实测记录

### 3.1 正常设备（`data/sensor_normal.csv`）

| 项 | 结果 |
|---|---|
| Agent 调用的 MCP 工具 | `read_sensor_summary` → `detect_anomalies` → `diagnose_fault` |
| 异常检测 | `status = normal`，6 个测点均无持续偏移，`max_abs_shift_z = 0.0` |
| 故障诊断 | `健康（无持续异常）`，健康度 **100**，`primary_diagnosis = null` |
| 维修动作 | 未触发（正常态按 SOP 直接短路，不写盘） |
| Agent 结论 | 判定为正常态，无残留风险 |
| 端到端耗时 | 约 **35 秒** |

### 3.2 过载设备（`data/sensor_overload.csv`）· 完整六步闭环

| 步 | 工具 | 结果 |
|---|---|---|
| 1 数据读取 | `read_sensor_summary` | ok |
| 2 异常检测 | `detect_anomalies` | ok，`critical`，`max_abs_shift_z = 38.04` |
| 3 故障诊断 | `diagnose_fault` | ok，主判 `overload` 置信度 0.936（特征 4/4） |
| 4 维修方案 | `plan_repair` | ok（工序 / 备件 / 安全措施 / 验收标准） |
| 5 模拟维修 | `simulate_repair` | ok，生成维修后复测数据 |
| 6 维修验证 | `verify_repair` | **success**，最大残留 **1.28σ**，持续异常点 1611 → 0，`residual_fault = null` |

- 健康度：**20 → 100**
- 端到端耗时：约 **2~3 分钟**（与本机性能有关）

### 3.3 失败→重规划→修复（`data/test/test_03_repair_failed.csv` 配对 `test_02_bearing_fault.csv`）

| 轮次 | 维修目标 | verify 结果 | 最大残留 | 健康度 |
|---|---|---|---|---|
| 1 | `bearing_wear`（误用次选，模拟误诊） | **failed** | 28.52σ | 20 → 50 |
| 2 | `overload`（重规划后按主判） | **success** | 1.28σ | 50 → 100 |

`residual_fault` 在第 1 轮直接指回 `overload`（置信度 0.859），Agent 据此完成纠错。
