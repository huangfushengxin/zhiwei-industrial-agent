# 智维（ZhiWei）工业设备智能运维闭环 SOP

当用户要求对工业设备做运维分析、故障诊断、检修或"修好它"时，按下列六步执行。
每一步都必须**真实调用**智维 MCP 工具（工具名形如 `mcp_zhiwei_ops_..._<tool>`），
不要凭已有知识直接作答，也不要跳步。

## 六步闭环

1. **数据读取** — `list_scenarios` 列出可用数据集，或 `read_sensor_summary` 查看某数据集的测点概况。
2. **异常检测** — `detect_anomalies`，确认是否存在持续偏移、影响了哪些测点、严重等级。
3. **故障诊断** — `diagnose_fault`，得到故障类型、置信度与判据。
4. **维修方案** — `plan_repair`，得到是否停机、工时、安全措施、分步工序、备件与验收标准。
5. **模拟维修** — `simulate_repair`（**写盘工具**）。首次调用时审批卡会出现，
   请用户选择「本会话允许」以便后续步骤自动继续。
6. **维修后验证** — `verify_repair`，用维修前数据的基线对比维修后复测数据。

也可以直接调用 `run_closed_loop` 一键跑完整闭环（同样是写盘工具）。

## 判定标准

- **维修成功**：`verify_repair` 返回 `status = success`（维修后无持续异常，各测点残留偏移 |z| < 4）。
- **部分修复**：`status = partial`，异常显著减轻但仍有残留故障。
- **维修失败**：`status = failed`，异常未改善或仍然严重。

## 失败重规划（必须执行）

`verify_repair` 未返回 `success` 时，**不允许**声称设备已修好。必须：

1. 说明上一次为什么没通过（残留哪些测点、残留多少 σ、残留故障候选是什么）；
2. 重新规划：提高维修彻底度（每次 `effectiveness` 加 0.5，上限 1.0），必要时补充排查项；
3. 再次 `simulate_repair` → `verify_repair` 复验；
4. 最多尝试 3 次；仍未通过则明确报告"需人工介入"，并给出建议。

## 最终回答必须包含

- 设备健康度（修复前 → 修复后）
- 故障结论与判据（哪些测点、什么方向、多少 σ）
- 维修动作（工序要点与涉及备件）
- 维修前后数据对比（各测点偏移变化与改善幅度）
- 是否通过数据验证；未通过则说明重规划过程
- 残留风险与后续建议

## 约束

- 不要修改 `data/` 下的原始数据；维修后数据写入 `data/repairs/`。
- 没有经过 `verify_repair` 验证，不得声称维修成功。
- 报告结论时必须引用工具返回的真实数值，不要自行编造。
## 异常恢复：诊断错了怎么办（Day 4）

如果维修后验证未通过，**首先要怀疑诊断本身是否错了**，而不是简单重复同一种维修：

1. 看 `verify_repair` 的 `residual_shifts_sigma` 与 `residual_fault`：
   **哪些测点还没回来**，就说明第一轮维修没覆盖到这些测点对应的故障。
2. 回到 `diagnose_fault` 的候选列表，比较主判与次选的**特征差异**：
   哪一类故障能同时解释"已恢复的测点"和"仍异常的测点"。
3. 用 `simulate_repair` 的 `repair_target` 参数显式指定新的维修目标故障，
   重新模拟维修，再用 `verify_repair` 复验。
4. 报告里必须写清：**第一轮把什么误判成什么、为什么没修好、第二轮改成了什么、结果如何。**

允许"先按次选候选维修 → 验证不通过 → 改按主判候选维修 → 验证通过"这种朴素但真实的纠错路径；
不允许在验证不通过的情况下直接宣称修好。
## 输出纪律（必须遵守）

- **直接给出最终结论**，不要向用户反问，不要征求确认。
- **禁止**出现"请告诉我""我可以按你指定目标继续执行""如果你知道该文件实际应有异常…""需要我继续吗"这类**后续选项式结尾**。
- 如果数据不足以判断，就直接写"数据不足以判断"并给出建议，而不是反问用户。
- 报告结尾停在结论与建议上，不要追加任何待用户确认的下一步询问。
